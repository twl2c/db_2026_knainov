# Нормализация базы данных

Я проверил свою базу данных на нормальные формы. Явных нарушений не нашёл. Таблицы разделены по смыслу, поэтому одни и те же данные не приходится хранить в нескольких местах.

## 1НФ

Все значения в таблицах атомарные, то есть в одной ячейке хранится одно значение. Например, для файлов используется отдельная таблица `attachments`.

Если бы я хранил файлы прямо в `messages`:

```sql
file1 VARCHAR(255),
file2 VARCHAR(255),
file3 VARCHAR(255)
```

это было бы неудобно, так как количество файлов было бы ограничено.

Поэтому используется отдельная таблица:

```sql
CREATE TABLE attachments (
    attachment_id SERIAL PRIMARY KEY,
    message_id INT NOT NULL,
    file_name VARCHAR(255) NOT NULL,
    file_type VARCHAR(50) NOT NULL
);
```

## 2НФ

Здесь важна таблица `chat_members`, потому что у неё составной ключ:

```sql
PRIMARY KEY (chat_id, user_id)
```

`role` и `joined_at` относятся именно к участию конкретного пользователя в конкретном чате.

Проблема появилась бы, если бы туда добавить, например, `chat_title`:

```text
chat_id | user_id | chat_title | role
```

Название зависит только от `chat_id`, поэтому ему место в `chats`, а не в `chat_members`.

## 3НФ

Хороший пример — таблица `messages`.

Если бы в ней были:

```text
message_id | user_id | username | email | text
```

то пришлось бы повторять имя и email пользователя в каждом его сообщении.

При изменении email пришлось бы обновлять несколько строк. Чтобы этого не было, данные пользователя находятся в `users`, а в `messages` хранится только `user_id`.

```sql
CREATE TABLE users (
    user_id SERIAL PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    status VARCHAR(20) NOT NULL
);
```

Таким образом, данные пользователя и сообщения не смешиваются.

## BCNF

Для BCNF я проверил основные зависимости:

```text
user_id -> данные пользователя
chat_id -> данные чата
message_id -> данные сообщения
(chat_id, user_id) -> данные участника
```

Во всех случаях слева находится ключ, поэтому дополнительных изменений для BCNF не требуется.

## Аномалии

В текущей базе аномалий я не обнаружил.

Если бы пользователи, чаты и сообщения находились в одной таблице, могли бы появиться:

* **аномалия обновления** — при переименовании чата пришлось бы менять его название во всех сообщениях;
* **аномалия вставки** — нельзя нормально добавить чат без сообщений;
* **аномалия удаления** — при удалении последнего сообщения можно случайно потерять информацию о пользователе.

В моей структуре это решается разделением данных на `users`, `chats`, `messages` и другие таблицы.

## Итог

Текущая структура соответствует 1НФ, 2НФ, 3НФ и BCNF. Существенных изменений в существующие таблицы для этого не требуется.
